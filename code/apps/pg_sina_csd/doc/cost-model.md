# SQLerate 阶段成本与状态估计

本文记录 `adaptive-exec-path` 的规划模型，供论文方法描述与后续校准使用。模型在 Guest 的 PG 扩展中运行；设备 CSF、FEMU 与 SNIA 不参与成本规划。下面的字节数和时间都是规划估计，不能当作实测结果。

## 规划范围与数据来源

HOST/CSD 候选在 PG 的扫描、合法连接组合及上层 Path 搜索中比较，不再固定一棵物理树后才选执行位置。原始 HOST、原始 PG 优选树的完整 CSD 转换，以及安全 Query 改写后的共享搜索结果均保留为完整候选；见 [规划说明](planning.md)。本次只改变候选生成与比较时机，以下设备成本公式不变。以 PG 的过滤/连接输出行数 `plan_rows`、HAVING 之前的组数 `numGroups` 为起点，再恢复并行区域的全局行数、传播表达式分组范围及 Join 乘数约束；资源预留还可使用已验证外键域的统计容量上界。扫描输入行数读取 `pg_class.reltuples`；字符串 NDV、NULL 比例与平均长度来自 `pg_statistic`。缺少字符串统计时，NDV 暂用最多 200、平均长度 32B，均是明确的回退假设。不同列/关系的字典值可能重合，目前按其 NDV 之和估计，未假设跨表相关性。

HOST 使用 PG 原有路径成本模型，并在路径比较前修正扫描缓存成本；设备子树加上返回成本后换算为 PG cost 单位，使其上层算法由 PG 正常枚举。CSD 使用编译后的设备表示和实际算法重新计价，不把 PG 总成本统一除以 CU 数。模型输出统一为毫秒。filter-only 的既有计划改写仍复用逐节点增量估价，不受此次搜索改动影响。

每个节点保留 H（HOST 节点、子树可混合）和 D（完整 CSD 子树）两种候选。H 可接收 D 的元组流并支付边界成本，D 不接受 HOST 中间结果。Hash Join 的 build/probe、Sort 的生成 run/归并、聚合状态的更新/合并/输出属于一个算子的内部生命周期，整体选址。不能把原生 Hash 的 MultiExec 状态当普通元组输出；需要 mark/restore 的原生 Merge Join 内侧同样保留接口。Partial Aggregate→Final Aggregate 只有在明确实现可合并状态传输时才可作为两个独立算子跨侧执行；本次不新增此执行能力。

## 并行阶段

PG 的参考点是 `costsize.c` 的并行扫描、Gather/GatherMerge、Hash Join 与 Aggregate：只缩短可并行工作，单独计入启动、传输、建表和最终处理。DuckDB 的参考点是 `physical_hash_join.cpp`、`physical_hash_aggregate.cpp` 和 `physical_order.cpp` 的 sink/local state、combine、finalize/source 阶段；这里按本项目实际运行时计费，不假设已具备 DuckDB 的全部并行能力。

规划器复用 `qp_parallel_boundaries` 和 `qp_pipeline_source`，与执行器使用相同的 pipeline 可并行性判定。只沿 probe/投影链传播并行性，不越过 build 边或阻塞边界。FDM 按 4/2/1MiB 块、列批次、控制/结果/IO 缓冲选 CU 数，先缩小块，再减少 worker。FDM 是 IO 内存，不能作为 workmem。

对一个阶段，令 W 为可分配 worker，T 为任务数，C 为单 CU 完成全部可并行工作的估计时间：

```text
waves = ceil(T / W)
parallel_compute = waves × C / T
schedule = waves × parallel_task_ms
stage_time = serial + parallel_compute + schedule + combine
```

T≤1 或 W≤1 时按单 CU 估计，不额外收费并行波次。扫描按物理输入块数估计任务，已完成 Hash Aggregate 的 source 按组数/向量容量估计。最后不足一轮的任务也占一个波次。该公式假设任务均衡，是尾部不满和调度已知条件下的估计，不声称预测了真实任务倾斜或所有共享锁竞争。

| 阶段 | 处理方式 |
| --- | --- |
| Heap/Index 扫描、投影、Hash Probe | 只有位于已标记 pipeline 中才按任务波次缩放 |
| Hash Build | worker 追加/编码按 build 输入的 pipeline 缩放；协调端 bucket 重建另按全部 build 行数串行收费 |
| 无分组聚合 | worker 更新局部状态，协调端按 CU 数×聚合数合并 |
| Hash Aggregate | 按实际布局判断局部表是否能够同时放下；放得下则计局部更新与分组分片合并，否则计共享更新及键更新串行争用项 |
| Sort | run 内比较可随已标记的上游 sink 并行；多 run 归并和最终输出单独按串行收费 |
| Merge Join | 无 Hash 的设备 Join 实际走 Merge；未证明有序的输入分别计排序，再计两路归并及输出表达式 |
| 已排序分组聚合、Materialize、Set | 按当前执行方式计费，不因配置了多个 CU 就自动缩短 |

CPU 单价仍复用 PG `cpu_tuple_cost`、`cpu_operator_cost`，乘 `host_cost_ms × csd_cpu_ratio`。表达式数是工作量代理，不是逐指令周期模拟。新增 `parallel_task_ms`（默认 0.02ms）只表示并行任务波次的调度成本；它和既有 CPU 换算系数都是待实测校准的初值。不能把默认值写成设备测量结论。

内部 NVM 带宽、PCIe 链路仍按共享总带宽计算，不乘 CU 数。当前内部读取与计算时间相加；本次没有假设尚未证实的全面读算重叠。HPCP 按其链路工作与前台工作的未覆盖部分估计，也不预支后续查询的缓存收益。

## 状态布局与生命周期

估计实现位于 `src/planner/cost.c` 与 `cost_model.h`。容量增长和槽位大小对照设备 `plan.c`、`sort.c`、`dictionary.c`；这些是模型里的布局估计，不新增设备 ABI 或改变执行器内存配额。

| 状态 | 估计方式 |
| --- | --- |
| Hash build | 每列按实际压缩格式：PG int2/int4/bool/date 为 4B+1B NULL；int8 为 8B+1B；其他值为 16B+scale/dscale/NULL。每行再加一个 4B next 和两个 4B bucket。容量从 128 起按 2 次幂增长 |
| Hash Aggregate | 单整数键保留紧凑键格式；多键按整数/字典 ID 或完整 cell 区分；聚合值是对齐后的 cell+count。记录对齐到 16B，哈希槽 8B，最多使用 7/8 的记录容量，容量从 128 起翻倍 |
| CU 局部聚合 | 先估计一张全局表，只有全部 CU 局部表与全局表、两份最低排序工作集都能放下时才估计局部模式；最低工作集按公开run/窗口/向量/结果缓冲布局近似，私有元数据留余量，不再保留两份最大排序额度 |
| Sort | cell 记录加字符串独立载荷、长度字段；字符串平均长度沿直接列引用回溯到 PG 统计，计算生成字符串用 typmod/32B 回退；另计 run 描述、spill token、IO 缓冲。行数据与字典正文同时存在时分别计费 |
| Set/Materialize | Set 按最多输入行数的不同值和 1/2 装载率估计 16B 槽位；Materialize 按实际 cell 行估计。Set 未恢复所有表达式形态的精确 NDV，属于偏保守的基数上界 |
| 字典 | NDV×16B entry，2 次幂的 4B hash head、字符串正文；rehash 暂存新旧 hash head。正文/entry 按 64KiB 页取整，页描述暂按 48B/页估计 |
| 表达式暂存 | 每个活动执行副本按表达式数×256 行向量估计；不是 2048 行 Heap 列批次，后者在 AFDM。执行器按需分配，故这部分是预留估计 |

Join 先构建右侧，再在保留 build 表时消费左侧；Sort/Aggregate 在消费输入时积累自己的状态，随后释放上游状态并输出。模型分别维护“输出期间存活”和“EOF 后仍保留”（Set/Materialize）的状态，以及构建峰值，避免无条件累加所有已完成节点的工作集。小表初始分配与随后增长也分开处理。字典为查询共享状态，只计一次；允许随其他工作集增长被驱逐，没有新增固定 25% 字典配额。hash/sort reserve 来自现有执行器，不是规划器新加的内存限制。

这仍是静态生命周期近似：并行分支的瞬时分配、分配器元数据、表达式惰性分配、CTE/InitPlan 多消费者重用等可能影响实际峰值。估计不会覆盖或代替统一 workmem 分配器的硬限制。

## Spill 与串行归并

- **Sort**：按照实际 1MiB run（受 sort quota 限制时缩小）、每个输入的64KiB行窗口、含字符串时的额外64KiB文本窗口和可用内存估算归并路数，没有额外32路上限。先计必须驱逐的 run 写出与最终读回；run 超过 fan-in 时，再计完整中间归并的读写。CPU 分开计算 run 内排序和跨 run 的堆比较。
- **存在性 Hash Join**：单键纯等值、无残余条件、直接基表扫描构建侧时，利用已有列NDV判断增长屏障去重后是否能留在内存；初始分配仍按最大可容纳的二次幂容量计费，不直接用NDV代替实际初始占用。缺失统计或唯一键本身放不下，保留通用spill估计。去重的键解码、哈希和比较计串行CPU，不除以CU数量。
- **Hash Join**：INNER 沿实际 4 分区 Hash spill 计 build/probe 写出读回，超大分区按 build 批次增加 probe 重读；SEMI/ANTI/LEFT 容量不足时沿现有排序归并回退估价，保留的 build 前缀不会重新扫描 Heap。没有假设递归 radix repartition。实际倾斜仍须实测校准。
- **Hash Aggregate**：容量不足时按 key/value/count 中间记录和输入量上界估计冲刷，再计外部合并 CPU；没有伪造精确的溢出组分布。
- **Set/Materialize**：按超出可用容量的部分估计一次写出读回。
- **字典**：可驱逐正文按共享剩余内存估计，一写一读是最低换出换入工作量；随机反复换入、rehash IO 放大仍不能由 NDV 单独准确预测。不能用这个下界认定实际 spill 放大已经解决。

## 可观察性与验证要求

SQLerate 的 EXPLAIN 新增串行 CPU、并行 CPU、调度、最终处理、字典工作集、FDM 预留及 worker 数；`CSD Stage Estimates` 按设备节点列出任务数、CPU、状态需求、估计常驻、可用额度和 spill。`Estimated Peak Workmem` 是常驻峰值估计，不能与完整逻辑工作集混为一谈。H/D 节点选择仍显示在 SQLerate 外层。未选中的设备候选保留汇总估计；原有强制 CSD 快路径不一定调用成本规划，不保证产生上述估计字段。调度按 pipeline 波次计一次，不对链中的每个 SQL 节点重复收费。

`tests/planner_cost.c` 检查单块不能多 CU 加速、不满一轮的开销、压缩 Hash 布局/容量跳变、分组表 7/8 容量边界，以及 64/256MiB 条件下内存增加可减少外排。集成验证只使用正式查询目录，冷启动核对结果与 EXPLAIN，不按查询编号修正模型。

论文实验还需要用既有执行 profile 比较：预测/实测阶段墙钟、协调 CPU、worker CPU、workmem 峰值及 spill 字节，并单列模型误差。构建成功、结果相等和模型预测准确是三个不同结论；在校准完成前不能声称 SQLerate 总能选中实测最快路径。

## 完整五模式冷启动测量

同日基于上述扩展版本，完成正式 22 条 SQL×五种 exe_path 的 110 次独立冷启动测量，结果全部一致。资源保持 4 CU、256MiB workmem、64MiB FDM，PG shared_buffers=128MiB、work_mem=4MiB。五种模式统一通过 auto_explain 保存实际执行树，没有 ANALYZE/TIMING 节点插桩；计时包含计划日志交付。数据与分析保存在 `results/tpch.F1pZUv/`：`timings.csv`、`plans.json`、`summary.json`、`report.md`，原始 SQL/计划日志一并保留。

累计延迟分别为 HOST 49.893s、filter-only 434.489s、CSD 无 HPCP 23.705s、CSD 有 HPCP 22.788s、SQLerate 27.537s。SQLerate 实际选 Q1 全 HOST，Q2/Q21 仅 Limit 在 HOST，其余 19 条全 CSD。本轮最低延迟命中 1/22，在最低值 5% 内 13/22；正确性通过，最优延迟目标尚未达到。

该历史测量暴露了 Q1 的估价对象错误：通用设备候选被估计需要约 6.46GiB spill，但强制 CSD 使用的专用聚合快路径实际只使用约 1.90MiB，spill 为零。该版本在 select_plan 选中卸载以后才换成专用快路径；此错误已由下节记录的候选与基数修正解决。Q1 贡献了 SQLerate 相比本轮事后逐查询最小值的额外延迟约 76%。

此外，相同 CSD 树仍有自适应规划及结果/计划日志交付的额外开销；当前 SQLerate 没有关闭 HPCP 的设备候选；PG 基数估计误差会放大边界成本（Q9 估计 60,150 行，实际 175 行）。Q18 虽确有读写各约 206.6MiB spill，设备路径时间仍从约 1.23s 低估到实测约 5.74s，不能只根据带宽换算认定 spill 时间或性能已合格。

Q4、Q21 另做了两轮交错冷启动复测（`repeats.csv`），所有结果一致。Q4 初次 HPCP 的大幅优势、Q21 初次 SQLerate 的 27.5% 回退均未稳定复现，不能作为稳定收益/退化的证据；运行时波动原因尚未定位。原始 110 次测量没有被复测值替换。每次清缓存也意味着本轮不能验证 HPCP 对后续暖缓存查询的收益。

## 估价对象与基数修正

候选比较之前先调用与强制 CSD 相同的单表快路径编译器；成功时按每 CU 最多256组的局部表、表达式向量、部分状态行和最终合并计价，不再先估通用树、选中后替换实现。Q1 的8个聚合超出了通用 spill 行的16-cell上限，但融合聚合用另一种部分状态布局，不能把前者的全明细排序成本套到后者。

将 PG 并行区域折叠到 CSD 前，先按 Gather 的实际规划 worker 数及 PG 的 leader 贡献恢复全局行数；Hash Join 的共享 build 输入一同恢复，私有 build 和 Nested Loop 内侧保持原口径。这里只修改计划副本，不改变 HOST 原生树。

参照 DuckDB 聚合统计传播，沿编译后的列引用追溯 YEAR 的日期来源，用 pg_statistic 的直方图和MCV年份范围限制不同值数，再与其他分组列NDV组合。缺少来源、统计或支持的类型时保留PG估计；统计范围只用于估计，不限制实际结果。Q9 的日期NDV=2406，年份范围为7，国家NDV=25，分组估计由60150修正为175。保留PG的HAVING选择率，不以TPC-H实测结果硬编码组数。修正后的行数用于状态预留、下游排序与返回成本，并保存在实际提交的设备计划中。

第一阶段正式 Q1/Q9 在当前PG新配置（4 worker上限、2GB shared_buffers、16MB work_mem）下分别冷启动验证，见 `results/tpch.nQpmRt/`。HOST/强制HPCP/SQLerate结果全部一致：Q1为2990.300/823.128/828.322ms；Q9为2570.281/1155.328/1173.423ms。Q1现选融合CSD，设备估计660.025ms、spill=0、峰值估计2129808B，实测1993152B；Q9返回成本由58.689ms降为1.040ms，预计175行，设备成本961.704ms。该阶段尚未修正Q18的spill阶段时间，不能据此宣称整体模型已准确。

## 聚合状态容量与 spill 阶段修正

Q18 的第二个根因是 `lineitem.l_orderkey` 的采样NDV仅389264，实际约150万。按前者会误判多份CU局部表可以共存；合并真实分组时才溢出。现在单列、已验证外键可用其引用唯一键域的统计规模约束聚合状态容量。它是资源上界估计，不是“所有父表键必然出现”的断言，不提高HAVING输出行数，也不改变结果语义。强制CSD与SQLerate均在编译通用计划时应用这些估计，避免模式之间再次使用不同的执行布局。统计或FK不支持时保留原估计；很稀疏的FK覆盖仍可能使这个容量上界偏保守。

另沿编译表达式证明分组键是否全部来自某个Join的probe侧：若成立，分组数不能高于probe输入行数，不将一对多匹配产生的明细行数直接当分组数。此约束同样适用于Index Join，不需要修改连接顺序，也不依赖查询编号。它将Q18外层分组状态从约52万组约束到约13万组，消除了256MiB下最终Sort的虚假溢出预测；这里仍没有猜测HAVING最终只返回9组。

真实Hash Aggregate溢出时，模型按容纳组数估计刷出次数、部分key/value/count行、run生成及归并。无序键使用均匀占用近似；单列键依据PG的相关系数平方，在随机和物理聚集两端之间插值，避免对连续键反复高估重复部分状态。CPU单列计入部分行序列化、run比较、堆归并、逐行解码及重新聚合；协调端的行处理采用现有HOST标量CPU换算，不乘向量加速比，也不除以所有CU。其余向量工作仍保留原来的并行波次模型。

Spill读写各按总字节的一半近似计费：读使用internal_mbps，写使用internal_write_mbps（当前默认100MB/s）。写值表示包含依赖请求与重入等待的有效吞吐，不是原始NAND写峰值；SF8实测中原1000MB/s初值明显低估外部路径，按完整CSD及Index Join图的墙钟、CPU和spill对照作经验校准。它不是SNIA资源查询返回的保证，换设备仍需校准。每64KiB重入I/O另按已有parallel_task_ms计调度工作；Sort按实际run、归并窗口和轮次计记录复制。无需新增设备命令、配置项或算子协议。

## 完整索引游标的访问量修正

## 独立扫描的交付与HOST并行消费

独立扫描已生成PG可直接引用的类型化列，不把其交付按重新解码Heap计费。CPU按真实运算、访问行数和输出行数计价，常量、列引用、已绑定参数不增加算术指令数。预计批次/续交数至少覆盖输入块任务，避免只用总输出行数除以返回容量，漏计高过滤率扫描的块末尾工作。已有result_batch_ms默认0.25ms，来自当前系统读取及续交各约0.14ms的细分记录；PCIe字节成本另计，后续平台仍应校准。

设扫描各阶段的总I/O时间为I、按现有任务波次折算的CU时间为C，有效参与者L=min(CU数,任务数)。独立扫描估计 I+C−min(I,C)×(1−1/L)，不把CPU简单除两遍。单CU或单任务仍为I+C，保留较短阶段的填充/排空份额。完整设备树沿实际pipeline source计算读算重叠；HOST返回与内部列块的物化分别计价。

在HOST连接处保留独立输入候选，防止PG在扫描层提前剪掉异构重叠机会。设原节点成本T、原/新输入成本差Δ、该HOST节点自身CPU为H、新CSD输入运行时间为D，则候选总成本为 max(新启动成本,T+Δ−min(H,D))。本实现只在直接父Hash/NestLoop比较，Hash分批、参数/顺序不兼容和私有重放形态不抵扣；不声称对任意多阶段并发图求解精确的资源关键路径。输入CPU与上层HOST CPU用不同执行资源，Join的build/probe状态仍同在HOST。

HOST索引的缓存折扣仅作用于I/O，保留PG的B-tree下降、二分比较、缓冲引用及元组/谓词CPU价格。早期对驻留索引额外降低每层CPU费用的做法已取消，避免大量重复探测的热路径被低估。Q3仍有跨表相关基数误差，详见planning.md最新验证；模型尚未达到所有热查询最优。

当前决策保持纯统计模型：估价使用现有PG统计、设备物理属性和缓存驻留记录，不执行Join采样，不将验收实测行数写回规划器。现有单表统计无法完整表示跨表谓词相关性；Q3仍有基数及路径误选，作为已知精度限制明确报告。

## Semi/Anti 索引连接的缓存扣费修复

原生HOST候选的缓存修正曾将一次完整内侧索引扫描的价差乘外侧行数。PG对SEMI、ANTI和inner_unique连接可能只读到第一个匹配，原连接成本没有包含这些完整扫描，因而产生过量扣费，Q4最终被截成0ms。

现在在原生Path阶段，保留同一索引的缓存后startup/total价格，调用PG原有initial_cost_nestloop/final_cost_nestloop重新估价，仅替换内侧输入价格；PG的match_count、匹配比例、提前结束、重扫与CPU费用均保留。临时价格在正常及ERROR路径均恢复。将差额用于选中原生计划的缓存修正，不再在这些节点重复乘完整内侧价差。只处理有真实缓存价差、内侧为索引扫描且可能提前结束的连接；没有额外设备请求或运行SQL采样。

定向热测 `results/q4-q10-fix.GZzqtM/`：Q4原HOST候选从0恢复为230.928ms，共享搜索选157.028ms的CSD扫描orders→HOST Semi Index Join及聚合排序。三轮查询主体中位HOST306.3ms、filter-only181.1ms、修改前SQLerate316.0ms、修改后175.1ms；修改后规划4.5ms、执行139.4ms，SQL总时间195.9ms。设备4CU/256MiB workmem/64MiB FDM，PG配置不变，只预热一次，填充模式双开HPCP/DCP。Q4与同时采集的Q10优化前基线共36份结果一致、72份FDM检查为0、实际spill为0；两项PG组件CTest通过，未跑全量。

## 参数化索引、短路过滤与扫描CPU预算

Q8的错误不能简单归为CSD估得太低：原选中方案只有小型part扫描在设备，主要耗时在HOST全量扫描lineitem后探测orders/customer。现有l_orderkey采样NDV=389264，使索引扫描估15行，但PG匹配外键后的连接行数对应平均约4行，诊断实际也为4行。现在只对纯FK等值、无额外过滤的参数化索引，使用PG连接行数/外侧行数修正CPU访问量；不假定子表覆盖全部父键，也不按这个比例把索引I/O打折。连接行数本身仍来自PG。

参数化索引是用外侧当前行的键查找内侧表。PG原先可能按所依赖基表的大量行数摊销索引I/O，但连接已经筛掉了大多数探测。现在依据当前外侧Path的估计行数和PG参与者因子重新调用cost_index，再用PG的initial_cost_nestloop/final_cost_nestloop重新计价，保留SEMI/ANTI提前结束。Q21冷诊断中，原生HOST顺扫会提前缓存Heap，后续lineitem索引shared read约1.7万块；CSD扫描的异步填充未及时覆盖相同探测，混合路径约9.8万块。当前修正了探测摊销，没有建立精确的查询内缓存到达时序模型。

Q19原HOST估992.599ms、实际执行约638ms，存在高估。HOST多AND条件现在按PG的security/cost顺序及已有前缀选择率计短路工作，不再把每个后续条件计在所有行上；最终Gather与子扫描的参与者不同，CPU允许向上或向下修正。设备侧也有低估：逐行Heap处理/内部物化、直接PG结果编码不再一概乘向量加速比，表达式部分仍使用现有csd_cpu_ratio和CU波次。直接扫描按所需Heap前缀及输出列编码计费，内部单元物化保留完整预算；依据物理边界而非执行模式区分。

## 缓存停止与流水线估价的一致性（2026-11-02）

HPCP/DCP是可选的填充目的地。连接的现有驻留位图表明全部目标已驻留，或两个目的地均达到各自准入限制时，PG通过FEMU插件已有vendor配置暂停当前执行的接收。插件使用已有RX_STOP解除设备接收环；它不再生成带缓存标志的新图，已执行图也因接收环解除而停止登记和发送。仍在复制的块先完成或撤销引用，之后不会继续持有FDM。下一查询重新判断是否需要填充，不能永久关闭。仅DCP满、HPCP仍可接收时继续HPCP，反之亦然。32MiB初始化接收池继续保留；“停止开销”指不再产生新的DMA/接收块工作，不指归还初始化池或抹去此前开销。

成本端只对未驻留的目的地估计可选PCIe填充量：`max(HPCP开启 ? 1-file_fraction : 0, DCP开启 ? 1-shared_fraction : 0)`。两个缓存的页面集合可能不同，此处是保守的集合并近似，不是精确交集估计；执行端仍以实际准入为准。CSD输入继续内部NVM→FDM，不因HOST缓存命中扣除内部读取成本。

流水线内的LOAD与计算对单任务仍有依赖，但不同任务能重叠。模型沿已有pipeline source归属累计I/O和并行CPU，再按`min(I/O, CPU) * (1 - 1/有效CU)`扣除重叠一次。Hash build归入build输入；分组sink归入其输入；协调、combine及依赖驱动的spill不参与抵扣。此前只为独立扫描计算重叠、对完整设备算子链简单相加，导致全CSD候选被系统性高估。没有改变实际任务调度，也没有降低spill带宽价格。

Sort沿执行器实际规则检查直接且唯一的LIMIT消费者，估计TopN保留的`limit+offset`状态及全输入比较成本。状态能放下时不按完整输入虚构外排；放不下、共享/物化引用、谓词或无界时仍估完整Sort。估价和执行共用边界判定，避免选中之后才发现使用另一种实现。

对于带残余谓词、同一键域的ANTI连接，PG独立性估计有时退化到一行。自适应HOST搜索现在与已有设备模型使用同一DuckDB半/反连接20%不确定性回退，并同步更新PG提前结束的匹配比例；只在已验证同表列或单列FK键域时使用，不改变原生host-only基准。它仍是统计回退，不能证明真实选择率。

重复索引探测的PG I/O价格已经包含跨probe复用。观测缓存和这种复用不能对剩余I/O连续打折：分别从单次探测估计出发，取`min(PG重复探测I/O, 单次探测I/O的驻留修正)`。CPU全部保留，不因shared_buffers命中被额外削减。Q21诊断还表明跨表连接行数本身可相差数十倍，此修正不宣称解决所有基数误差。

## Join分组上界、扫描与索引早停（2026-11-02）

本轮只修改估价及估计行数传播，未修改SQL、算子执行实现、设备资源、默认速度参数或按exe_path区分物理算子。参考本地DuckDB统计传播与等值列绑定的思路，继续使用PG现有统计，不做Join采样。

- 分组键若可证明全部由某个Join输入决定，分组数以该侧估计输入行数为上界，支持probe/build两侧。INNER等值连接的两侧键等价，允许把一侧键换到另一侧做来源证明；LEFT的右侧可能新增一个NULL组。参数化Index Join的内侧行数是每次探测行数，不能作为全局分组上界。Sort无过滤时直接继承输入逻辑行数，避免对已经收紧的子节点再次按比例折扣。
- 表达式CPU只统计运算，列引用、常量、参数及已计算的聚合引用不重复收费；聚合更新单独计费。候选属性用负column的Q_AGGREF记录未编码运算，不能误认为全部是免费引用。轻量候选没有恢复完整指令编码。融合/通用设备链都采用同一计数规则。
- 所有扫描都复用scan.c的Heap walker，在最后一个所需列停止。估价的Heap前缀比例因此也对内部扫描生效；返回PG原值和内部cell的物化仍分别计价，没有把返回格式优化套到内部单元。
- 纯等值SEMI/ANTI Hash的去重容量不再仅凭低采样NDV断言“放得下”。复用已有单列、已验证FK键域的状态容量上界；它不用于提高选择率，也不宣称子表覆盖全部父键。稀疏FK仍可能使容量估价偏保守。超过容量时，只有INNER走分区外排，SEMI/ANTI/LEFT按设备实际路径计排序、复制、串行归并及spill；已保序的probe输入不重复排序，保留build前缀仍须排序。
- 本地过滤后的Index Semi/Anti可以在首个合格匹配停止。设每键候选数N、本地条件通过率p，预计访问数为`(1-(1-p)^N)/p`，p=0时为N，p=1时至多1。p来自现有IndexScan输出估计与键NDV，不使用验收行数；关联残余条件或缺少统计时保留完整候选访问量。Heap页访问继续使用相关性与有界索引缓存模型，预取和键倾斜不因此变成精确可知。

Q3的来源证明之前只识别probe侧，还漏掉INNER等值键可换到build侧：分组中的lineitem订单键与orders订单键等价，因此整组键可由已过滤orders输入决定。当前组数从2599962收紧到1219592，预测聚合状态从620757120B降到310378624B，spill从671575784B降到447090718B。仍高于上轮实际90931组、实际spill=0：剩余差额来自订单日期与明细发货日期的跨表相关性，普通列统计不能精确表达。本轮Q3只检查正式EXPLAIN与来源证明组件，不重跑Q3性能，不宣称统计问题全部解决。

Q4的排序归并回退曾被错算成便宜的Hash外排，且低NDV让候选被判零spill。针对性诊断中该候选实际读写各400556032B、峰值约170MiB，而原估spill=0。修正容量与回退算法后拒绝这一候选；随后补足Index Semi本地过滤早停，使原PG设备Index Join候选的冷估价从7159.054ms降到4603.642ms，混合候选仍约6684.865ms。最终三轮冷启动完整设备实际执行中位5164.771ms；估价仍有偏差，但相对次序正确。

Q15主要是完整设备链的CPU高估：原生设备图的两个lineitem扫描每个约4325ms，现在按真实运算及Heap前缀每个约2314ms；完整设备估价9616.213→5521.024ms。此前完整设备执行约5.2秒而混合约5.7秒，模型反而把混合估得更便宜。HOST及混合路径仍有绝对成本误差，本轮没有用查询专用系数调整HOST价格。
