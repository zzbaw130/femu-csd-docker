# 原生 PostgreSQL 配置对照

使用同一个 SF1 数据库和 PostgreSQL 12.22，仅运行 host-only；两个配置各执行正式 `tests/guest/queries/` 的全部 22 条。每条前都重启 PG、清空 shared buffers 和 Guest page cache，不复用上一条查询的缓存。auto_explain 仅记录计划，不开启 ANALYZE/TIMING；Q15 仍为创建视图、SELECT、删除视图的耗时之和。

| 参数 | 原默认配置 | 新配置 |
| --- | ---: | ---: |
| max_parallel_workers_per_gather | 2 | 4 |
| shared_buffers | 128MB | 2GB |
| work_mem | 4MB | 16MB |

`max_parallel_workers=8`、`max_worker_processes=8` 保持不变；Guest 仍为 8 vCPU/8GiB。work_mem 是各执行节点/worker 的额度，不能解释为整条查询的总上限。

## 主要变化与实际执行证据

- Q1 下降35.8%，Q6下降17.1%，Q12/Q14/Q16/Q19下降约19%–21%。Q1/Q6的计划 worker 数由2增至4；Q3/Q5/Q9的计划最多使用3个，并非所有查询都采用4个。三项配置同时改变，本轮不能分别量化各参数的独立贡献。
- Q13 上升136.0%。旧计划是并行 LEFT Hash Join + Sorted Aggregate，实际启动2个 worker；新计划改为串行 RIGHT Hash Join + Hash Aggregate。补采的实际执行统计显示，旧计划有8806/9273个8KiB临时读/写块，新计划临时读写为0，却仍从约1.19秒变为2.81秒。这是规划器选择了较慢的串行方案，不能归因于内存不足或 spill。
- Q18 上升20.4%。实际 worker 由2增至3，连同leader使内侧未共享的 lineitem Index Scan + Aggregate 从3次完整执行变为4次，每次都读6001215行，相当于约1800万→2400万行的重复处理。临时读写由各4021个8KiB块降为0，物理 Shared Read 总块数约158608→158586基本不变，但重复扫描增加了缓存访问和计算。增大并行上限不保证该计划更快。
- Q2/Q11/Q22本轮也变慢，Q10有小幅波动；未采集足够的逐节点时间，不将这些变化硬归因为某个参数。Q2/Q22的计划结构及计划worker数未改变。修改配置记录时机后额外冷启动验证Q22为779.624ms，与新配置首次768.486ms接近，保存在新配置结果目录的`22.host-only.repeat.*`，不混入合计。

Q13/Q18 的补采使用原始 SQL，通过 auto_explain 开启 ANALYZE、BUFFERS，关闭逐节点 TIMING，分别存为两组结果目录中的 `*.host-only.profile.log/err`。其结果也与对应普通运行一致。带插桩耗时只用于定位，不混入上表。

## 生效与复现

`scripts/guest/start-postgre.sh` 写入新配置；当前 `/data/tpch_s1/postgresql.conf` 已修改并重启生效，pg_settings 的 pending_restart 均为 false。以后启动和冷启动都保留新值。

Guest 运行：

```sh
sh /home/femu/tests/tpch-cold.sh -n 3 -b 2GB -w 4 -m 16MB
```

当前统一入口记录配置并测试五种路径，HOST对照读取cold.csv的host_only_ms列；本节历史实验只测原生PG，不用旧CSD记录宣称新配置下的加速比。
