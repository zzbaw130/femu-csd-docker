## 三层职责与已落实的基础改造

- PG调用原规划器，基于其选定的物理计划做有条件rewrite，准备Heap/Index映射和资源编排；不是按TPC-H编号生成固定计划。
- SNIA FEMU插件把标准batch中的计算、存储与依赖转换成通用设备图；不解释SQL列、Join或聚合。
- FEMU执行CSF、依赖、CU及内部LOAD/STORE/I/O完成事件；SQL解码、列向量、集合和算子状态都在 `csd-programs/pg_sina_csd` 的设备SO中。
- PG读取设备CU和FDM容量，以及workmem容量CSF的64位返回值；并行槽和缓冲布局据此安排。CU子context的分配逐级计入查询根预算，仍受物理workmem池限制；FDM只保存输入输出及控制信息。
- 扫描解码窗口2048行、表达式批次256行，与4/2/1MiB读取块分离。主要Scan/Filter/Projection/Join/Aggregate及Sort输入可直接消费列批次，保留跨I/O、重复匹配、未满输出及错误位置。
- CU局部聚合、共享构建和Combine分别管理局部/共享状态；namespace页请求和spill可在设备图内部完成并重入。普通worker完成值减少了不必要的AFDM控制读取，必要的共享表增长/spill屏障仍保留。

## 尚未完成

性能门槛已经通过，完整基础改造仍不能据此宣告结束：

1. 构建表增长/重建、聚合合并及部分阻塞边界仍有协调端工作，应先按上述当前profile确认关键路径，再优化；不能声称8CU持续满载。
2. Sort及spill归并Source仍有串行推进，部分复杂DISTINCT、过宽状态、不支持表达式和有序扫描条件保留行适配；主路径列化不等于所有PG执行形态均向量化。
3. 字符串字典与整数集合自身尚无spill；预算不足会明确失败。已有Hash/Sort/Aggregate低内存spill与取消回收测试，不能替代这两类状态的容量处理。
4. 部分阻塞阶段仍由PG观察完成并提交后续任务；继续减少可避免的停顿，同时保留资源安全边界，避免把SQL编排搬进FEMU固件。

旧阶段局部计时不再混入当前成绩；具体实现提交和组件验证记录保留在 [development.md](development.md)。当前只证明仓库规范22条与已覆盖回归，不宣称完整PostgreSQL语法支持或DuckDB同等性能。
