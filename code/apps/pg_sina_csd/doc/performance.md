## 结合基线后修复的退化

含字符串时，分页接入曾直接跳过原批量Filter，让全部行进入较重的投影路径。现在条件在原始Heap字节上批量筛选；Filter只需要本地只读字面量字典，存活输出才进入全局分页字典。数值与延迟文本扫描复用原解码函数。Filter临时内存不足时，重新解码也正确接入分页游标。

Q10/Q14/Q22原先失败的原因是Join已经选中匹配行后，懒物化等待字典资源被保存成永久投影错误；重入还会提前取下一对匹配。向量投影现在保留匹配对及列位置，标量适配保留待输出行，消费插入结果后才推进，没有通过忽略错误或放宽对比解决。

Q19普通延迟由此前2,023.912ms降至本轮631.756ms。[独立冷启动profile](../../../../results/tpch.vsChA6/19.profile.log)中，主流水线平均活跃CU由此前2.36提高到6.47、利用率80.9%；workmem峰值3,872,560字节，spill读写均为0。这是计算/调度路径恢复的收益，不能归因为减少spill。profile执行时间593.261ms不混入普通计时。

[本轮同环境基线对照](../../../../results/tpch.4KMWGl/timings.csv)只替换独立编译的 `5e6d2ffcc` 设备SO，Q10/Q14/Q19/Q22均通过，确认错误来自后续执行修改。旧版完整22条的[历史成绩](../../../../results/tpch.g6Dk0d/timings.csv)为CSD合计13,836.763ms；本轮15,799.221ms仍有差距。两个全量成绩不是同轮交替A/B，不能把全部差异直接归因于算法，也不宣称本版每条都快于旧版。

四项64MiB组件检查及对应ASan/UBSan/泄漏检查通过：字典超预算换页、run自持多列正文/8CU归并/取消、原始文本Filter与分页字典共同执行，以及Join匹配行等待另一CU后在向量/标量路径恢复。保留新功能，未通过退回不支持spill的实现获得性能。只保存基线对照与最终验收结果，临时构建及中间失败的诊断轮次已清理。

## 职责及改造核对

| 要求 | 当前实现与证据 |
| --- | --- |
| 三层职责 | `src/extension.c` 调用PG原规划器；`src/planner/plan.c` 转换其选定计划并保留Join树。SNIA的 `femu_batch_scheduling.c` 只转换计算、存储、参数与依赖；FEMU `csd.c` 只管理图、CU及I/O完成事件。SQL语义在设备 `pg_sina_csd` SO中，没有查询代理进程。本轮22条均实际完成，计划和最终结果核对通过。 |
| 列批次与继续位置 | 设备 `scan.c`、`plan.c`、`query_vector.h` 中Scan/Filter/Projection/Join/Aggregate主路径消费列批次；Join重复匹配及未满输出保留游标。计划组件覆盖非首列多键、NULL、重复匹配、残余条件及输出接续。 |
| 读取与向量粒度 | 读取块按FDM采用4/2/1MiB，扫描窗口2048行、表达式批次256行，分别保存I/O和块内位置，不按整块最坏行数预留所有列。 |
| 并行局部与共享状态 | `plan.c` 区分CU局部聚合/排序、共享Hash构建、Combine和Source；8/16/64 CU组件核对结果及释放。配置8 CU不代表全过程满载；本轮Q19利用率见上文。 |
| 持续推进 | PG `src/executor/plan.c` 的callback按完成值续交页面任务，SNIA提交设备图；FEMU按就绪队列和I/O完成时间推进内部LOAD/EXEC/STORE及重入。共享表增长仍在必要屏障内执行。 |
| 真实预算与spill | PG `pg_sina_read_resources` 读取CU/FDM及workmem容量，默认查询预算等于设备workmem；FDM限制缓冲布局。设备分配器 `cs_workmem.c` 将CU/算子子context实际分配逐级计入查询根及物理池，搬移期间旧、新分配都计费。64MiB组件覆盖排序正文spill、结果及资源回收；不把发生spill直接当作物理内存不足证明。 |
| PG语义 | 使用PG生成的计划、类型及排序信息；设备精确numeric、NULL和表达式短路保留原语义。本轮22条结果逐字节对照PG；组件另覆盖多键、numeric scale、NULL及SUM/AVG等。该证据覆盖当前支持的查询形态，不代表任意PG语法。 |

## 默认字典换入换出的当前验证

当前资源验证下限为64MiB；不再增加或复测更小预算的压力场景。默认 `pg_sina_plan` 创建可换页字典，正文、ID目录、哈希桶及全部缓存/访问状态计入同一查询预算，消费者共用稳定ID。正常结束释放临时token和workmem，取消由设备会话回收未确认token。SNIA/FEMU请求及AFDM结果布局保持不变。

当前实现复用最近ID的正文定位，并将最终结果批次的文本按ID顺序读取后填回原行列。部分批次因内部NVM读取暂停后，只编码新增行。索引数组按实际文本列数分配，属于设备workmem。PG先合并读取结果前缀，再按 `str_bytes` 回传实际字符串，省去固定1MiB字符串区的整块读取。消费者组件覆盖元数据换页、UTF-8/substring、NULL/短路、Join、聚合、分轮归并、输出及取消清理；此前组件验证还覆盖部分批次追加和真实NVM请求重入。

### 64MiB功能验证

`pgSinaDictionary64MiB` 从默认CSF入口执行Scan→Sort→输出，用模拟NVM完成真实NEED_*重入。它是设备代码的组件验证，不是Guest SQL延迟成绩。

| 项目 | 当前结果 |
| --- | ---: |
| 查询总预算 | 67,108,864字节 |
| 输入行数 | 524,288 |
| 字典正文 | 83,021,120字节，超过预算 |
| 峰值workmem | 62,078,208字节 |
| 总STORE / LOAD | 3,536 / 3,614 |
| 完整文本、整数、NULL及顺序 | 全部匹配 |
| 结束后token、workmem、上下文 | 全部归零 |
| ASan / UBSan / 泄漏检查 | 通过 |

Sort改为run自持变长字符串正文，并按有序行序存储。相同64MiB夹具的LOAD由519,060次降至3,614次，累计读取由34,017,116,160字节降至236,847,104字节，减少约99.3%；STORE由1,605次增至3,536次，因为run也携带正文。这是模拟NVM的累计请求字节，不是Guest实测SSD带宽；仅保留这组前后对照说明数据表示的收益。

新增 `pgSinaSortPayload64MiB` 使用相同524,288行，额外覆盖超过12字节的公共前缀、非排序键文本列、空串、5/20/255字节文本、重复ID、NULL、串行和8 CU局部run归并，以及STORE/LOAD完成但未确认时取消。串行STORE/LOAD为4,458/5,266，8 CU为4,467/2,424（并行次数随任务分配变化）；峰值分别62,886,496与65,531,536字节，均低于64MiB。完整值、顺序和资源回收通过，这两个目标及新增Filter/Join恢复目标均通过ASan/UBSan/泄漏检查。回归测试还限制累计LOAD，避免只验证结果而放任每行换页退化。

### 64MiB开发用例（不属于TPC-H验收）

以下为排序正文表示的针对性开发验证；与上文256MiB完整TPC-H成绩分开记录。每次测量独立冷启动，临时SQL在使用后清理。

另用现有冻结 `part` 表做开发验证：读取 `p_name,p_comment,p_partkey` 并按三列排序，完整20万行逐字节匹配host。开发SQL使用后清理，不替代标准TPC-H验收。[64MiB普通计时](../../../../results/sort-owned-text-64m.aY6YPA/timings.csv)为host **688.362ms**、CSD **1,680.322ms**；[profile](../../../../results/sort-owned-text-64m.aY6YPA/profile.log)无spill，峰值53,555,120字节，Sort Sink/Source累计CPU为619.506/227.050ms，流水线平均活跃CU约1.09。该场景性能仍不合格，不能归因于内存不足；本轮消除了超预算排序的大量字典随机读取，没有解决扫描intern及本地排序的全部CPU/并行开销。

真实设备spill另用同一 `part` 表读取 `p_name,p_comment,p_type,p_brand,p_mfgr,p_container,p_partkey`，按 `p_name,p_comment,p_partkey` 排序，20万行完整匹配host。[普通计时](../../../../results/sort-owned-text-spill-64m.JCT11D/timings.csv)为host **927.654ms**、CSD **2,872.087ms**。[独立profile](../../../../results/sort-owned-text-spill-64m.JCT11D/profile.log)确认查询预算67,108,864字节、峰值67,094,416字节，spill读50,987,008字节、写29,425,664字节，验证了设备内部STORE/LOAD及正文归并路径。该用例包含真实内存压力，但平均活跃CU约0.93，不能将全部延迟差距归因于内存不足，性能仍未合格。临时SQL和大结果文件已清理。
