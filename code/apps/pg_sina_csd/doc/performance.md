## 本轮改动与Q22证据

Scan/Filter对字符串直接使用保留的Heap字节视图，SUBSTRING生成临时切片；仅过滤所用的列不进入字典，需要交给后续算子的字符串才物化。向量求值器引用InitPlan的完整int128参数和实际numeric scale，不能安全用SIMD的比较继续用精确宽整数。所有工作仅位于SQL设备程序与其私有记录中，不扩展FEMU/SNIA协议。

本轮修改前Q22冷启动为host626.459ms / CSD674.103ms，结果正确但性能未合格。修改后两轮独立冷启动为CSD340.172/334.444ms，同轮host796.876/672.904ms，均正确且实际卸载；完整轮Q22为998.388/317.586ms。样本中的host也有波动，不能把单个比值当作稳定提升倍数。

## Q18：尚未解决的并行与I/O边界

[Q18独立profile](../../../../results/string-vectors.errqnQ/q18.profile.log)显示工作内存峰值15869952字节、无spill，不能归因于256MiB工作内存不足。输入包含lineitem的有序索引扫描/回表及聚合，后续还有Index Join。查询树墙钟8524.691ms，协调端Hash build累计CPU3980.428ms、Scan累计CPU2386.971ms，host提交5732次。

这说明应优先细分有序索引聚合所在的串行阶段与页面请求开销，再判断全表输入是否更适合并行扫描/Hash Aggregate。不能把8个执行槽或某阶段峰值8CU解释为全程8CU满载，也不能因AFDM使用66791816字节接近上限便直接扩容。

## 长期目标仍在进行

目前尚未完成整个通用执行器的列批次接口：Join/分组聚合仍有逐行适配，局部与共享状态、Combine/Finalize覆盖和跨块持续执行仍需继续优化。完整轮通过证明当前这批SQL能加速，不证明这些实现要求全部完成。

保持PG负责SQL/计划编排、SNIA负责通用请求适配、FEMU CSD固件负责通用I/O与计算调度；SQL算法留在设备程序中。后续先根据Q18阶段证据推进，FDM仍保持64MiB；只有实际测量证明必要才测试256MiB。
