## 职责及改造核对

| 要求 | 当前实现与证据 |
| --- | --- |
| 三层职责 | `src/extension.c` 调用PG原规划器；`src/planner/plan.c` 转换其选定计划并保留Join树。SNIA的 `femu_batch_scheduling.c` 只转换计算、存储、参数与依赖；FEMU `csd.c` 只管理图、CU及I/O完成事件。SQL语义在设备 `pg_sina_csd` SO中，没有查询代理进程。22份验收计划确认实际走CSD路径。 |
| 列批次与继续位置 | 设备 `scan.c`、`plan.c`、`query_vector.h` 中Scan/Filter/Projection/Join/Aggregate主路径消费列批次；Join重复匹配及未满输出保留游标。计划组件覆盖非首列多键、NULL、重复匹配、残余条件及输出接续。 |
| 读取与向量粒度 | 读取块按FDM采用4/2/1MiB，扫描窗口2048行、表达式批次256行，分别保存I/O和块内位置，不按整块最坏行数预留所有列。 |
| 并行局部与共享状态 | `plan.c` 区分CU局部聚合/排序、共享Hash构建、Combine和Source；8/16/64 CU组件核对结果及释放。实际Q9记录8个工作槽、峰值8个活跃CU。 |
| 持续推进 | PG `src/executor/plan.c` 的callback按完成值续交页面任务，SNIA提交设备图；FEMU按就绪队列和I/O完成时间推进内部LOAD/EXEC/STORE及重入。共享表增长仍在必要屏障内执行。 |
| 真实预算与spill | PG `pg_sina_read_resources` 读取CU/FDM及workmem容量，默认查询预算等于设备workmem；FDM限制缓冲布局。设备分配器 `cs_workmem.c` 将CU/算子子context实际分配逐级计入查询根及物理池，搬移期间旧、新分配都计费。4MiB组件覆盖真实spill、结果及资源回收；不把发生spill直接当作物理内存不足证明。 |
| PG语义 | 使用PG生成的计划、类型及排序信息；设备精确numeric、NULL和表达式短路保留原语义。22条最终结果逐字节对照PG，组件另覆盖多键、numeric scale、NULL及SUM/AVG等。该证据覆盖当前支持的查询形态，不代表任意PG语法。 |

## Hash诊断与组件检查

普通查询验收后，另用规范Q9做独立冷启动profile：[记录](../../../../results/final-profile.OTf7mX/9.log)。workmem峰值149575424字节，AFDM52637832字节，spill读写均为0，8个工作槽且活跃峰值8。两张增长表分别搬移25690112、22020096字节，共45.5MiB；内存操作CPU分别30.812、25.667ms，重建CPU分别16.682、20.292ms。这些区间包含在Hash Build协调CPU内，不能重复相加。profile执行时间837.346ms不混入普通计时。

`moved_bytes` 只统计扩容更换地址时旧表的请求字节数；原地扩容、首次分配和失败分配不计入。关闭profile不取表操作时钟。此字段在PG/设备SO私有计划中，修改布局必须同步部署两端。

本次使用现有构建产物运行原生计划（含4MiB实际spill与回收）、8/16/64 CU并行计划及4MiB设备容量查询，共5项针对性检查，全部通过。容量查询项只验证容量返回；实际spill证据来自原生计划中的低预算用例。上一算法阶段的原生/8CU消毒器、混合宽度打包Join键及Guest堆布局检查已通过；本次算法不变。

## 后续低内存扩展：可恢复的集合探测

整数集合扩容实际失败后复用内部STORE/LOAD；列批次、标量投影和Hash/Merge/Index Join残余条件均保存继续位置。标量投影保存当前输入及聚合结果，恢复后不重新取行；残余条件不提前推进候选，Index消费者保留当前行及准备进度；聚合先求完所有参数再修改状态，批次保留已消费行号。没有修改PG/SNIA/FEMU接口。

原生计划及8CU两项组件、对应两项地址/未定义行为和泄漏检查通过。新增4MiB用例覆盖15万个集合输入、重复键、有无NULL、IN/NOT IN及取消重入；另有18组无输入标量投影和24组Hash/Merge/Index的INNER/LEFT/SEMI/ANTI条件，均核对结果、真实spill、4MiB峰值和资源回收。普通查询回归只验证常规路径，不能代替这些低内存组件证明。

## 默认字典换入换出的当前验证

默认 `pg_sina_plan` 已创建可换页字典，绑定扫描、向量/标量表达式、Join、聚合、Sort、索引和结果编码，原 SNIA/FEMU 请求接口不变。初始化导入、BUSY 重试与正常/取消清理均由查询执行对象保存进度。

`pgSinaDictionaryNativePlan` 验证默认入口，使用模拟 NVM 驱动真实 NEED_* 重入：

| 路径 | 正文字节 | 查询预算 | 已核对 |
| --- | ---: | ---: | --- |
| 串行 Scan→Sort→输出 | 5,188,800 | 4MiB | 32,768 行、全部文本/整数/NULL、完整顺序 |
| 4CU Scan→局部Sort→归并→输出 | 10,377,600 | 8MiB | 65,536 行、实际 worker 计时、完整顺序 |
| STORE/LOAD 完成但未确认时取消 | 同串行夹具 | 4MiB | 设备 workmem 归零，模拟会话回收未确认 token |

正常结束要求发生 STORE 和 LOAD，峰值不超预算，所有 token、workmem 和上下文归零。字典描述符和访问状态也在预算内。消费者组件另外覆盖元数据换页、稳定 ID、UTF-8/substring、NULL/短路、Hash/Merge/Index 条件、共享及局部聚合、分轮归并和最终输出恢复。十一项相关原生检查和十项 ASan/UBSan/泄漏检查通过。

Guest 使用现有 SF=1 冻结的 `part` 表，以8MiB查询预算执行开发用只读文本排序，12万行完整结果与冷启动原生PG逐字节一致。该临时SQL用于验证字典接入，不替代标准TPC-H验收。更大的20万行输入曾触发120秒超时，未视为通过。

在构建和消毒器检查结束后独立采集的[8MiB诊断](../../../../results/tpch.CmeGxj/dictionary-8m.profile.log)显示：205,058个字典条目、正文5,221,321字节，查询峰值8,373,360/8,388,608字节，spill读18,848,546,816字节、写1,312,948,224字节，执行54,707.725ms。正文加ID目录/哈希桶和算子工作区确实竞争预算，但如此高的I/O放大仍须排查，不能仅以出现spill就判定性能合格。
